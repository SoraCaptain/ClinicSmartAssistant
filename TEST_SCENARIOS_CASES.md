# ClinicPilot AI - Data-Grounded Test Scenarios and Expected Answers

## 1. Test Baseline

- **Current date used for date-sensitive tests:** 2026-10-22
- **Default patient:** P001, John Doe
- **Known allergies:** Penicillin and Peanuts
- **Valid clinics:** C001 and C002
- **Valid doctors:** D101-D104
- **Valid treatments:** T001-T005
- Newly created booking IDs may vary because they are generated by the application.
- Natural-language wording does not need to match the examples exactly. An answer is correct if its facts and actions match the acceptance criteria.
- The assistant should not invent unavailable doctors, treatments, clinic services, or schedule availability.
- **Booking confirmation gate:** when all required booking parameters (treatment, doctor, date, time) are complete, the assistant renders a booking summary and creates the booking only after the patient explicitly confirms it (for example, "yes"). The assistant asks only for missing parameters or for the explicit confirmation — nothing else.
- When exactly one doctor matches the chosen treatment's specialty (or exactly one treatment matches the doctor's specialty), the assistant may auto-apply that unique match and state it, instead of asking an open-ended question.

# 8. Booking Workflow and Slot Filling

For booking tests, assume all requested times are available, as required by the assignment. After a successful booking, the created record must be persisted and appear in `GET /api/bookings` and the frontend booking panel.

## BOOKING-CREATE-01: Fully specified valid booking

**Turn 1**

> Book a Dermatology Consultation with Dr. Elena Rostova on November 20, 2026, at 2:30 PM.

**Expected behavior**

- Resolve Dr. Elena Rostova to D103.
- Resolve Dermatology Consultation to T003.
- Use P001 as the current patient.
- Normalize the date to 2026-11-20.
- Normalize the time to 14:30:00.
- All required slots are complete: render a booking summary (treatment, doctor, date, time) and ask for explicit confirmation. No booking is created yet.

**Expected summary**

> Here is your booking summary: Dermatology Consultation with Dr. Elena Rostova on 2026-11-20 at 14:30. Shall I go ahead and book it?

**Turn 2**

> Yes, please book it.

**Expected behavior**

- Call the booking tool or `POST /api/bookings` exactly once.
- Save the booking in the database.
- Clear the pending draft.

**Expected confirmation**

> Your Dermatology Consultation with Dr. Elena Rostova has been booked for November 20, 2026, at 2:30 PM.

**Also accepted**

> Confirmed: Dermatology Consultation, Dr. Elena Rostova, 2026-11-20 at 14:30.

Both confirmations are correct. The generated booking ID and default status may vary according to implementation.

## ERROR-06: Missing required fields in direct booking API

**API request example**

```json
{
  "patient_id": "P001",
  "doctor_id": "D103"
}
```

**Expected API result**

- HTTP 400 or 422.
- A structured validation error identifies missing treatment, date, and time fields.
- No database record is created.

Both 400 and 422 are acceptable if used consistently and documented.

---

## ERROR-07: Unknown patient ID

**API request condition**

Call a booking endpoint with `patient_id` set to an unknown value such as `P999`.

**Expected API result**

- HTTP 404, 400, or 422, according to the documented API convention.
- The response clearly explains that the patient was not found or is invalid.
- No booking is created.

All three status choices can be considered correct if the behavior is consistent and documented. HTTP 404 is preferred when the endpoint treats the patient as a referenced resource.

# 14. Acceptance Summary

A test answer should be marked correct when:

- It is factually consistent with the six CSV files.
- It does not expose another patient's data.
